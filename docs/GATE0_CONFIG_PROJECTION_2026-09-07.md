# ConfigRead projection diagnosis

Date: 2026-09-07. Engineering consultation; no scientific reviewer verdict.

The two absent `tools.*.enabled` values in the actual checkpoint-012 startup report have a source-backed explanation: the `config/read` API discards these fields when it projects core configuration into its public response type. Their absence does **not** establish that the command-line overrides failed. It also does not independently establish that the actual winning overrides were false, because the old report retained only the presence of the layers and origins containers.

This finding concerns the exact audited release, Codex 0.151.0, commit `78c290807ce710180111df227df3b7a4fe845452`, with the runtime binary already pinned by the startup probe. Seven additional exact source files were retrieved through the GitHub connector and checked against the corresponding Git blob SHA-1 and byte lengths. Their SHA-256 inventory is `artifacts/GATE0_CONFIG_PROJECTION_SOURCE/20260907_001/MANIFEST.json`, SHA-256 `5d75ddbee78a502b27a1c38389e99ef3eed24cad2968128240ea4c89141f89b8`. Apache-2.0 LICENSE and NOTICE accompany those sources.

## Why the projection loses the controls

1. `ConfigManager::read` loads the requested cwd's configuration layers, merges the effective TOML configuration, converts it to `ConfigToml`, applies exact requirements and serializes it into JSON. It then **deserializes that JSON into `ApiConfig`** before returning it. This conversion is at source lines 133–145. [Exact config-manager service source](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/config_manager_service.rs), accessed 2026-09-07.
2. `ApiConfig.tools` is `Option<ToolsV2>`. `ToolsV2` contains only `web_search`; it has neither of the two enablement fields nor an additional flattened map to retain them. The surrounding `Config` does retain additional *top-level* fields, but that does not preserve unknown fields nested inside the typed `tools` object. See lines 156–161 and 254–292. This is consistent with the `ToolsV2` definition in the already extracted exact embedded `ConfigReadResponse.json` schema. [Exact API types](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server-protocol/src/protocol/v2/config.rs), accessed 2026-09-07.
3. The core configuration nevertheless resolves `tools.update_plan.enabled` and `tools.experimental_request_user_input.enabled` explicitly. The corresponding booleans default to true only when the optional tool configuration is absent; an explicit false produces false. Core utility-tool construction registers the respective handlers only when these resolved booleans are true. See configuration lines 2628–2643 and tool-plan lines 1119–1143. [Exact core configuration](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/config/mod.rs), [exact tool registration](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/tools/spec_plan.rs), accessed 2026-09-07.

Thus the public merged `config` object is not a complete runtime-control attestation. This limitation belongs in the observer interpretation; it does not justify silently marking the old report's `all_requested_controls_observed` field true.

## Smallest additional observation

Keep the completed startup observation and its raw result. Do not send the user another startup-only rerun solely to rediscover this projection. At the next already-required bounded, no-model metadata observation, retain narrowly filtered evidence from the existing `config/read` request with `includeLayers: true`:

- For these **two fixed paths only**, inspect the boolean leaf in the unprojected layer JSON, the winning origin metadata, and whether the matching layer is enabled. Never persist the raw layer/config response.
- Require the winning origin to be `sessionFlags`, with an unambiguous matching layer name and version, and the value to be the actual boolean `false`. Record only fixed path names, source-type enumeration and booleans describing these checks. Reject an absent value, changed type, ambiguous match, disabled winner, or conflicting/shadowing higher layer.
- Cross-check layer order and origins rather than accepting an arbitrary occurrence of false in a lower layer. `layers` is returned highest-precedence first **including disabled layers**; effective configuration and origins use only enabled layers. Requirement sources are separate, so preserving and evaluating the actual requirements remains necessary.
- Keep the result labelled a source-backed configuration observation. Actual full-client tool exposure, fresh context, subscription model selection and any other remaining boundary obligations stay separate until observed.

This route is possible because `config/read` returns each layer's original `JsonValue` directly; it does not deserialize it through `ToolsV2`. The source also returns origins for the winning enabled configuration layers. Exact requirements currently applied to configuration do not include either of these two tool-enable paths; any managed requirements must still be respected and inspected through their supported interface.

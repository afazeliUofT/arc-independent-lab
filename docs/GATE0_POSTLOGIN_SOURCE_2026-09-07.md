# Post-login metadata: exact native persistence and scope

Date: 2026-09-07. This is source consultation in the PI's shared workspace, not an independent scientific review. No native client, authentication request, or model was run for this consultation. The controlling source is Codex 0.151.0, commit `78c290807ce710180111df227df3b7a4fe845452`.

## Decision

Prepare one finite, human-launched post-login metadata process. It should retain the original HOME, CODEX_HOME, credential backend, runtime, configuration ancestry and policy inputs. It should send only initialization, filtered configuration and requirements reads, `account/read` with `refreshToken:false`, `account/rateLimits/read`, and `model/list`. No thread, turn, login, logout, reset-credit consumption or configuration-write request belongs in this protocol. A completed receipt must be reused rather than rerunning measurements when publication fails.

The new native process needs a narrowly defined permission beyond the one-time sign-in scope: **the pinned client may update the existing `~/.codex/auth.json` in place if its normal authentication lifecycle refreshes credentials**. Give only that existing file a same-path writable bind. Do not grant its parent directory write access, copy the credential, change backend, or permit parent code to read, hash or serialize its contents. Other writes remain inside the fresh project run. This is a proposed scope, not evidence that its additional permission has already been granted.

An offline cached account read could establish that the new file is usable and reveal a filtered account kind and plan enum. It cannot establish live endpoint authentication, a current quota snapshot, or successful loading of an applicable uncached cloud policy. After the completed sign-in, another separate offline-only round trip has limited value. Bundle the useful metadata questions into the finite live observation once its exact scope is authorized.

## Why a read-only credential mount with live networking is insufficient

`account/read(refreshToken:false)` skips its explicit refresh and obtains cached provider account state. That property belongs to the request handler, not to the entire process. See [account handler, lines 1019–1031 and 1108–1128](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/request_processors/account_processor.rs#L1019-L1128) and [provider account state, lines 389–418](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/model-provider/src/provider.rs#L389-L418), accessed 2026-09-07.

`AuthManager.auth()` may proactively refresh expiring or old credentials. The refresh implementation contacts the authority **before** persisting returned tokens. Therefore network-enabled execution with a read-only credential file can obtain replacement tokens and then fail to save them. Possible token rotation followed by persistence failure is an engineering risk inferred from this ordering; it has not been observed on this account. Recent sign-in is not proof that no refresh can happen during startup or unauthorized recovery. See [auth manager, lines 2341–2358, 2924–2945 and 3010–3026](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/login/src/auth/manager.rs), accessed 2026-09-07.

The exact file backend calls `create_dir_all` on the already-existing parent, then opens the existing file with truncate, write and create options, writes the serialized state, and flushes. It does not require a temporary sibling or rename. An existing same-path writable file bind is sufficient for this save path; the directory can remain read-only. This is an inference from the native code to be checked with a synthetic mount test before delivery. Initial path checks should reject symlinks, hard links, nonregular files or unsuitable permissions using metadata only. Native saving is an in-place operation; forced interruption or I/O failure during that operation remains a limitation of the client, and does not justify making a credential backup in the project. See [file storage, lines 178–227](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/login/src/auth/storage.rs#L178-L227) and [token persistence, lines 1555–1578](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/login/src/auth/manager.rs#L1555-L1578), accessed 2026-09-07.

## Startup, caches and managed policy

Startup installs a cloud-config worker and an online model-refresh worker. These can issue native metadata/authentication requests independently of the small JSON-RPC sequence. The observed process lifetime and outer mounts, rather than the request names alone, bound their effects. See [cloud loader, lines 64–86](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/cloud-config/src/bundle_loader.rs#L64-L86) and [models refresh worker, lines 37–62](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/models_refresh_worker.rs#L37-L62), accessed 2026-09-07.

Preserve an existing `~/.codex/cloud-config-bundle-cache.json` as an exact read-only input. Do not hide it to force a fresh request. The service uses a valid identity-matched cache, otherwise fetches a bundle for eligible account types. The native cache validates its version, signature, identity and expiry. A fetched valid bundle remains usable when cache saving fails; no writable cloud-cache grant is needed for this observation. The public projection of requirements is still not a full certificate of policy completeness, and a null result is not a general claim that no managed policy applies. See [cloud service, lines 49–57, 175–197 and 304–344](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/cloud-config/src/service.rs) and [cloud cache, lines 24, 39–106 and 128–165](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/cloud-config/src/cache.rs), accessed 2026-09-07. The latter file was fetched for this consultation; it is not a member of the earlier subscription-source archive.

Preserve an existing `~/.codex/models_cache.json` read-only as well. Model-cache write failure does not fail discovery. `model/list` uses `OnlineIfUncached`, and its returned presets can come from bundled, cached or online metadata. Do not report a catalog entry as a successful model invocation or proof of entitlement. See [model manager, lines 29, 240, 377–434 and 477–515](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/models-manager/src/manager.rs) and [model-list conversion, lines 13–24](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/models.rs#L13-L24), accessed 2026-09-07.

## Network and output boundaries

Sharing the host network namespace provides inherited network access; it is **not** an endpoint allowlist. Describe it exactly this way. Do not expose a host session-bus socket. Continue the existing empty-root filesystem boundary, exact runtime/config inputs, private backing for the same installation ID, and fresh project state/log writes. No scientific packet is needed for metadata observation.

For DNS and TLS, inspect only specifically chosen system resolver and trust inputs: ordinarily `/etc/resolv.conf`, `/etc/hosts`, `/etc/nsswitch.conf`, and the system CA bundle. These are proposed dependency inputs, not a claim that the exact binary's minimum trust lookup has already been measured. Resolve each selected system-file symlink to one regular file and bind that file read-only at the original lookup pathname. This preserves selected file content at the native lookup name, not the original symlink type or full chain; record both resolved source and destination. Never silently substitute resolver contents, disable certificate checks, mount all of `/etc` or `/run`, or reassign HOME/CODEX_HOME. Unexpected topology or missing required dependency should produce a filtered failure, not an automatic broader grant.

The parent should whitelist response fields, discard raw native output and notifications, and isolate optional metadata-method errors so a catalog failure does not erase a valid account or meter result. Initialization or configuration failure can still make later claims unusable. Bound each method and total process lifetime; do not retry automatically.

The exact schema archive supports account kind/recognized plan enums; meter bucket IDs, integer usage percentages, window durations and reset timestamps; and model identifiers plus supported reasoning-effort strings. Preserve reported bucket scope and observation time. Never retain email, account IDs, tokens, raw policy instructions, opaque cursor values or reset-credit identifiers. Report pagination incompleteness rather than silently calling a partial catalog complete. Unknown values should remain explicitly unrecognized.

A successful `account/rateLimits/read` establishes that the client obtained a live authenticated response from its configured Codex backend endpoint at that time. It does not establish entitlement to a selected model, the full reviewer tool boundary, or the remaining allowance of the hosted ChatGPT conversation. Rate-limit reads retrieve reset-credit details, while consumption is a separate operation that must never be sent. See [rate-limit handler, lines 1131–1204](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/request_processors/account_processor.rs#L1131-L1204) and [separate reset operations, lines 10–79](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/request_processors/account_processor/rate_limit_resets.rs#L10-L79), accessed 2026-09-07. No inferred hosted allowance percentage should be filled in; unattended model use stays paused without an authoritative meter for the relevant scope.

Schema provenance is the already-pinned local `artifacts/GATE0_CODEX_INTERFACE/20260907_001/schemas/experimental.json`, containing `v2/GetAccountRateLimitsResponse.json`, `v2/ModelListParams.json`, `v2/ModelListResponse.json` and `v2/ConfigRequirementsReadResponse.json`. This memo authorizes no native action and records no independent scientific verdict.

## Engineering observation, 2026-09-08

Nine targeted synthetic wrapper-control tests passed: actual versus fenced or qualified approval, credential and policy-cache content-read traps, protected-file topology and permissions, changed configuration provenance, the exact planned write grants, and refusal/reuse ordering. These are parent-control checks, not a native reviewer or network observation.

A separate local bubblewrap attempt used an entirely synthetic file to test the native `create_dir_all` plus in-place open/truncate/write pattern with a read-only parent. It stopped before the child with exit code 1 and stderr `bwrap: Can't read /proc/sys/kernel/overflowuid: No such file or directory`. The fixture content remained unchanged. The attempted command and result are preserved under `delivery/GATE0_POSTLOGIN_BOUNDARY_TEST/`. No real credential, Codex process or network request was involved. Consequently, exact-file persistence remains a source-backed inference; this sandbox did not supply an observed passing namespace test. No broader permission or alternative environment was requested to conceal that limitation.

The prepared human invocation now includes this small synthetic prerequisite before any real credential bind. `scripts/gate0_postlogin_boundary.py` requires the fake in-place write to succeed and both sibling creation and a read-only control-file write to fail. It additionally compares the resulting fixture bytes and enforces a ten-second process limit, two-second cleanup allowance and bounded streams. Five further synthetic control tests passed, including rejection of a changed namespace executable and a reported success without the expected actual fixture effect. A failed prerequisite stops native metadata startup within the same invocation; it is not a request for a separate diagnostic round trip.

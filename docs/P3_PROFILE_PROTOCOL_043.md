# Checkpoint043 development component profile protocol

Date: 2026-09-12. This plan is frozen before any development learner execution. It implements the next engineering dependency identified in checkpoint042. It does not admit a target experiment, select experimental resource ceilings, reopen native review, or claim a treatment outcome.

The driver receives only its explicit source bundle, the versioned operation counter, the N1/N3 reference modules, and `configs/P3_PROFILE_FIXTURES_043.json`. It has no target simulator, target panel, target goal, private paper, network client or native-model import. Its labelled tables are fabricated component fixtures, including internally conflicting identical inputs that need not describe a realizable environment.

## Prospective work

Run the named `test_reference_n1_043`, `test_reference_n3_043` and `test_profile043` conformance suites first, within the same wall allowance. A failure blocks profile cases. Then run each of three materially different component cases at small, typical and largest sizes, with three fixed repetitions in the declared order. Record every planned row, including rows that did not start. Sizes are 10, 85 and 245 retained transitions and 5, 20 and 45 macro words. The JSON fixture contract fixes the exact construction rules and expected conformance assertions.

The first N1 case maximizes repeated conflict work without furnishing a useful predicate: identical complete feature inputs have cyclic next labels, and thus no syntactic predicate can separate a conflicting pair. This deliberately avoids profiling only an easy positive terminating example. The second N1 case has an explicit preceding-observation distinction, exercises positive selection, count reconstruction and snapshot isolation, and discloses no target performance. The N3 case uses fabricated interfaces to inspect proposal enumeration and credit state transitions. These are component cases, not complete acquisitions.

The parent reserves one execution and retains the first report. The driver writes its initial report before executing a component, then atomically replaces that report after each component. A returned report, failed run, reserved-but-interrupted run, or an output directory with a pre-existing report is never silently remeasured. Repeating a command returns retained evidence or the categorical interruption. A new measurement requires a new explicit versioned receipt route.

## Limits and measurement

The inclusive outer wall cap is 300 seconds. The driver stops starting work before its 270-second internal wall cap, reserving the remaining outer time for termination, report finalization and the wrapper. Execute on exactly one available CPU, with a 2 GiB address-space cap and a finite CPU limit. Each profile runs in a fresh subprocess. Process and descendant CPU accounting, elapsed wall time, peak resident memory, logical operation counts, logical retained bytes, serialized output bytes and interruption are preserved. A worker that cannot finish yields a partial or categorical interrupted row. The driver saves a graceful partial report when it receives the wrapper's termination signal if the runtime can still execute Python; SIGKILL and unrecoverable host loss are recorded by the parent reservation protocol.

Host load is not controlled. Report that fact rather than calling the samples quiet or contended. The three repetitions characterize these declared development components; they do not establish a distributional confidence interval or a worst-case runtime guarantee. Python address-space limit and RSS are separate observations from the common logical retained-byte measure.

## Budget interpretation

The algebraic maxima are n <= 245 retained transitions, K <= 4 selected predicates, at most 3002 grammar candidates, at most 29890 transition pairs, at most 50 completed scored trials (55 completed recipes including five warm-up recipes), at most 45 macro words, at most 27720 raw proposals per assembly and at most 39 assemblies. They are provisional finite bounds until checked against exact implementation semantics. A measured update maximum is not a measured complete-acquisition maximum. Copies, serialization, diagnostics, validation, interruptions and all update multiplicities remain mandatory accounting components.

Checkpoint043 therefore reports `complete_work_budget_admitted: false`, leaves B_comp and B_mem unset, and supplies component measurements for the next review. Even a fully successful profile does not authorize the 240-world panel. A later complete-work derivation must name every mandatory component, validate its multiplicity and retained-object overlap, and apply checkpoint042's factor-two reserve and 25 percent audit allowance. Missing components cannot be filled by multiplying an arbitrary measured maximum.

## Evidence and claims

The public return is a full structured report plus the handoff receipt. It contains the exact code and fixture hashes, planned row identities, component assertions and resource metrics. It contains no target scores, goals, experiment verdict or new native usage. A component conformance failure blocks further component execution and is an implementation finding. Interruption leaves already completed rows unchanged and the remaining rows explicitly unmeasured.

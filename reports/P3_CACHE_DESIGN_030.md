# Stable cache-input proposal, checkpoint 030

Date and source access date: 2026-09-10. Status: **offline implementation and tests; no new native or model operation authorized or performed**. This is shared-workspace engineering, not independent scientific review.

The 028 report establishes changed host-cache metadata after an independent native-item stop. It does not identify the changed cache, writer, or bytes the reviewer saw. This proposal neither repairs that historical evidence nor waives its failed check. The earlier assumption that a read-only bind fixes input bytes was insufficient: another host process can modify the underlying inode. The pinned Codex cache implementation writes in place with `tokio::fs::write`; it does not guarantee atomic replacement. [Linux mount documentation](https://man7.org/linux/man-pages/man2/mount.2.html), [pinned Codex cache source](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/models-manager/src/cache.rs), accessed 2026-09-10.

## Proposed boundary and preserved policy

The only new content-read scope consists of `cloud-config-bundle-cache.json` and `models_cache.json`, under the already verified original Codex home. Their bytes are copied exactly into anonymous memory files and hashed for provenance; raw bytes are never logged or saved to the repository. This is a proposed extension of the earlier metadata-only treatment of these caches. It requires an explicit future control-scope amendment. It does not authorize reading, hashing, copying, logging, or relocating credentials or native configuration values.

The existing credential refresh grant is a same-path writable bind to the one existing auth file. **That grant is preserved exactly.** The parent receives only the auth device/inode metadata already collected by the authorized inventory and rejects a candidate cache alias to that inode before opening it. Symlinks, hard links, nonregular files, unexpected owners, group/world writable files, empty files, and files larger than 4 MiB are refused. There is no arbitrary filename parameter and no directory listing.

The unchanged configuration, installation identity, runtime, managed-requirements, account, model selection, and effective-profile checks continue to apply. No cloud-cache JSON field, timestamp inside cache content, model description, policy field, or signature is rewritten. The child sees the original cache pathname and original file permissions. Its cache inode and filesystem timestamps necessarily describe the private copy; this is recorded as a proposed storage change, not represented as authentic host inode metadata. Native validation remains responsible for accepting or rejecting the authentic cache content.

## Capture and launch contract

`capture_cache_inputs(codex_home, auth_metadata=...)` walks absolute directory components with no-follow directory descriptors. It observes both exact cache paths before capture, checks the opened inode against that observation and the forbidden auth identity, makes two bounded reads, and refuses differing reads or metadata. It then copies the exact bytes to Linux memfds and applies `F_SEAL_WRITE`, `F_SEAL_GROW`, `F_SEAL_SHRINK`, and `F_SEAL_SEAL`. A fresh component walk and observations of both names close the capture interval. Any observed mutation during the interval refuses the entire capture and closes all partial descriptors. [Linux open documentation](https://man7.org/linux/man-pages/man2/open.2.html), [memfd documentation](https://man7.org/linux/man-pages/man2/memfd_create.2.html), [file sealing documentation](https://man7.org/linux/man-pages/man2/F_GET_SEALS.2const.html), accessed 2026-09-10.

This establishes two equal reads and unchanged observed metadata; it is not an atomic filesystem transaction or a proof against a malicious privileged host. An adversarial writer that defeats these observations is outside the claim. Ordinary concurrent same-inode writes and rename replacements are explicitly tested. After successful capture, later host writes or replacements cannot change the sealed bytes. A cache absent during capture remains absent in the child's mount plan even if a host process subsequently creates it.

`CacheInputs.verify_origins` checks the prior metadata inventory. `apply_to_plan` replaces only the existing exact cache read binds in an already validated mount plan. Every non-cache argument, mount, runtime command, and policy field is preserved. Present caches use `--perms ORIGINAL_MODE --ro-bind-data LIVE_FD ORIGINAL_PATH`; absent caches receive no grant. The transform refuses unexpected, duplicated, missing, writable, renamed, or newly appeared cache grants.

The bubblewrap 0.9.0 implementation copies the input descriptor into a private temporary file, closes its child descriptor, binds the private file read-only, and unlinks the temporary pathname. This is a separate copy from the original host cache inode. The parent must keep the `CacheInputs` context alive through child creation and postchecks, use its exact `pass_fds` with `Popen(close_fds=True, ...)`, and close it on launch failure and after child reap. Saved plans redact live descriptor numbers and are marked nonreplayable. [Pinned bubblewrap implementation](https://github.com/containers/bubblewrap/blob/8e51677abd7e3338e4952370bf7d902e37d8cbb6/bubblewrap.c), [Python subprocess documentation](https://docs.python.org/3/library/subprocess.html), accessed 2026-09-10.

`verify()` checks the retained sealed memfds and hashes; it does not pretend to inspect a live child's mount namespace. `observe_sources()` separately records full before/after metadata and all differing field names for both paths without reopening their contents. A source-cache change is reported without writer attribution. It does not by itself change the sealed-input integrity result. Configuration, runtime, identity, scientific packet and reviewer-event failures remain separate invariant failures. This distinction requires explicit approval; it is not a silent relaxation of the 028 predicate.

## Validation and remaining machine measurement

The 25 tests in `tests/test_p3_cache_inputs_030.py` pass in this hosted Linux environment. They include actual kernel refusal of writes, shrink/grow operations, shared writable mappings and further seal changes; concurrent same-inode writes and replacements during/after capture; absent-file creation; auth-alias and symlink refusal; exact-mode/path preservation; descriptor inheritance through an actual Python child; cleanup after failure; output and deadline bounds with an actual synthetic child; and complete per-path metadata reporting.

Tests of the bubblewrap preflight's decision/report contract use mocked child results and are labeled as such. **No successful bubblewrap namespace mount was observed here.** The installed executable reported `bubblewrap 0.9.0`; its help invocation then exited 1 with `Can't read /proc/sys/kernel/overflowuid: No such file or directory`. No privileged retry, downloaded binary, or native client was used. Memfd creation/sealing itself succeeded. This Python build omitted seal constants, so the module uses the stable Linux UAPI numeric constants when absent; successful real syscalls, rather than constant availability, decide support. [Linux seal constants](https://github.com/torvalds/linux/blob/v6.8/include/uapi/linux/fcntl.h), [Linux command-number base](https://github.com/torvalds/linux/blob/v6.8/include/uapi/asm-generic/fcntl.h), accessed 2026-09-10.

The future single authorized reviewer invocation must run `probe_sealed_mount` **before reserving any native/model allowance**. It uses only fresh synthetic files under the project delivery directory, no real cache/auth content and no network. It changes the source fixture in place after sealing; a contained fixed Python program must then observe original bytes at the expected path, failed write/truncate attempts, continued absence of the second cache, refusal to create it, and no synthetic-auth mount. Anything other than `PASSED` stops the invocation before a native start. There is no fallback mount or separate human diagnostic request.

That preflight uses a new process group, an eight-second active deadline, two seconds reserved for cleanup, stdout bounded to 4 KiB, stderr bounded to 16 KiB, group kill, direct-child reap and a check that its process group is absent. The report retains bounded stderr only from this fixed synthetic subprocess, with phase, truncation, return code and cleanup evidence. Raw Codex/native protocol logging remains prohibited. It deliberately omits bubblewrap's separate `--new-session` so cleanup targets the whole inherited process group. OS process creation retains Python's documented noninterruptibility limitation; no universal wall-clock guarantee is claimed. A successful synthetic mount check establishes that tested mechanism on the target machine; it is not a fresh attestation of every subsequent native mount.

# Offline native lifecycle proposal 030

Date: 2026-09-10 UTC. Engineering work in the PI's shared workspace; not an independent scientific review. This document describes implemented offline code and generated fixtures. It grants no native execution or model allowance.

## Problem and evidence boundary

Run 028 made 88 successful broker calls, then rejected an `item/started` notification without retaining its exact item type. Its actual rejected type remains unknown. Source analysis established that the pinned client can emit a valid `contextCompaction` item that 028 rejects; it did not recover the missing historical type. The later cache-metadata failure is separate and remains the subject of the cache design, not this item-policy change. [Run028 forensic analysis in repository](https://github.com/afazeliUofT/arc-independent-lab/blob/b2f47e9442cbc5bd06490dd0d9fb0475a860aae9/reports/P3_RUN_028_REVIEW_AND_ROUTE_DECISION.md), accessed 2026-09-10.

The 028 code enforced thread/turn binding and turn-start replay checks, and its broker independently enforced request/call replay checks. It did **not** maintain a per-item started/completed registry. Describing strict per-item replay checks as an already-existing control would therefore be incorrect.030 adds that registry while retaining the distinct existing broker and turn controls.

## Complete pinned item classification

The pinned `ThreadItem` enum contains 19 types. 030 classifies all 19; seven are conditionally admitted and 12 refused. Classification completeness is not a claim that the entire native client or all nested schemas have been verified. The pinned source is `openai/codex@78c290807ce710180111df227df3b7a4fe845452`. [Item definitions](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server-protocol/src/protocol/v2/item.rs), accessed 2026-09-10.

| Item types | 030 policy and purpose |
| --- | --- |
| `userMessage` | Only the exact original text prompt, no client-provided origin or additional user message. |
| `agentMessage`, `reasoning` | Bounded transport text with source-defined fields; no memory citation or added origin. Text is never interpreted as a command or a verdict. |
| `dynamicToolCall` | Existing five broker tools only, no namespace, object arguments and source-defined status; the corresponding callback must match the canonical started item before the unchanged broker validates and executes it. |
| `functionCallOutput` | Only the previously source-closed `send_user_message_async` and `test_sync_tool` output names and original namespaces. No output execution or broker-outcome inference. Nested output is not newly interpreted. |
| `plan` | Newly admit a text-only proposed-plan item with exactly `type`, `id`, `text`; associated plan deltas require its active identity. This does not enable an `update_plan` native tool. |
| `contextCompaction` | Newly admit canonical lifecycle items with exactly `type` and `id`; require matching start and completion. Compaction changes retained model context and may entail native inference. It is not described as a text-only event or a free operation. |
| `hookPrompt` | Refuse an additional instruction source. |
| `commandExecution`, `fileChange`, `mcpToolCall`, `collabAgentToolCall`, `subAgentActivity`, `webSearch`, `imageView`, `sleep`, `imageGeneration` | Refuse effects outside the reviewer profile. Page images remain available only through the original manifested broker operation. |
| `enteredReviewMode`, `exitedReviewMode` | Refuse unapproved mode changes. |
| Unknown, missing or malformed type | Stop, recording only `unknown` plus fixed validation categories. |

The two new admissions are a proposed control amendment. They do not establish that either type caused run 028's historical stop.

## Monotonic session controls

`scripts/p3_event_policy_030.py` supplies a context-independent `Lifecycle` registry to `scripts/p3_reviewer_session_030.py`. The registry is never provided to the model and never reset by compaction. It holds at most 4096 item identities, each at most 256 printable ASCII characters. This uses the existing finite-turn item ceiling as an explicit monotonic registry ceiling. It retains raw identities and transient argument-comparison digests in RAM only; receipts do not expose or hash these values. The registry is cleared at session cleanup.

A second start with an existing identity, completion without start, second completion, changed type, mismatched delta or reused callback stops the session. Canonical item notifications require their exact source fields and integer timestamp. A dynamic item start must precede its callback, with the same call identity, tool, namespace and argument content. That ordering is emitted by the pinned app-server: it queues the canonical started notification before the `item/tool/call` request. The unchanged broker still independently checks its complete request envelope, bound thread/turn, authority, request and call identities, frozen evidence, time, call count and input-error ceiling. [Pinned dynamic item forwarding](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/bespoke_event_handling.rs), accessed 2026-09-10.

Turn response and completion `items` are snapshots. They are schema/class validated, and any registered identity must retain its type, but the snapshot does not start or complete registry entries. This matters because the pinned turn-completion payload may summarize the last agent message already delivered through its item lifecycle. [Pinned turn-completion construction](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server/src/bespoke_event_handling.rs), accessed 2026-09-10.

The additional source check for `functionCallOutput` found no completion-only exception requiring a weaker registry. `hook_runtime.rs` constructs a canonical function-output item from a standalone turn input and emits its start immediately before its completion. The native `send_user_message_async` handler instead emits a paired `agentMessage` lifecycle; its function return is transcript data. The stream handler explicitly ignores unexpected function outputs from the model stream. The existing restricted function-output names are retained, but their canonical lifecycle must still be paired. [Standalone input emission](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/hook_runtime.rs), [async message handler](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/tools/handlers/send_user_message_async.rs), [stream handling](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/stream_events_utils.rs), accessed 2026-09-10.

Successful `submit_verdict` still ends the parent loop at the accepted broker outcome. The final dynamic item can remain active: waiting for its native completion or treating a later native message as the verdict would change the existing outcome protocol. Likewise a synthetic challenge ends at the real broker's witnessed path refusal. Neither endpoint requires zero active registry entries. The report labels active item count explicitly.

Compaction creates no fresh thread or turn, grants no new tool, and does not reset elapsed deadlines, stream/queue limits, call identities, error counts, successful-read/refusal witnesses or evidence validation. The existing finite process CPU, wall-time, stream, frame and output limits remain applicable to all native activity, including compaction. A native internal compaction inference is not a newly sent parent `turn/start`; counting these concepts separately is necessary. The module does not estimate subscription usage from compaction count or duration.

## Notification grammar and diagnostics

The source `ServerNotification` definitions contain 81 wire methods. 030 enumerates all 81 for **categorical diagnostics**, with an offline equality check against the archived pinned source. Membership alone never admits a method. [Notification definitions](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server-protocol/src/protocol/common.rs), accessed 2026-09-10.

The prior admission policies remain for disabled remote control, sparse account limits, pre-thread account state, thread creation/settings/status, bound turn/item activity, token-usage metadata, witnessed server-request resolution, model verification and moderation metadata. The existing exact configuration, deprecation and disabled-Code-Mode warning classifiers remain unchanged. Reasoning deltas additionally require a matching active reasoning item and nonnegative source-shaped segment index. Agent and plan deltas require their matching active item. Replayed server-request resolution is refused.

The newly admitted outer notifications are `item/plan/delta` and `model/safetyBuffering/updated`. A targeted final source check corrected the draft policy's refusal of the second: buffering metadata can arrive with ordinary server text/completion responses without any native tool invocation. The session forwards it without selecting another model. This source establishes that it is possible in the current tool-restricted profile; it does not establish its probability or that it occurred in run 028. [Response metadata parsing and tests](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/codex-api/src/sse/responses.rs), [session forwarding](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/session/turn.rs), accessed 2026-09-10.

Buffering metadata requires the accepted thread, turn and current model; exactly the source-defined fields; a literal `showBufferingUi` boolean; UTF-8 string arrays for `useCases` and `reasons`; and `fasterModel` null or a UTF-8 string. The original 24 MiB protocol frame ceiling bounds this discarded passive payload. No additional per-field numerical ceiling is invented: the upstream schema supplies none, and an unsupported limit could recreate an ordinary-event false stop. The report keeps only the admission count and boolean recommendation-presence history. It never retains those native strings or follows a faster-model recommendation. Binding, effort, timers, witnesses and all broker controls remain unchanged. [Buffering notification schema](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/app-server-protocol/src/protocol/v2/model.rs), accessed 2026-09-10.

Deprecated `thread/compacted` remains refused because the pinned v2 route uses canonical compaction items. `turn/plan/updated` remains refused: its source emitter is the distinct `update_plan` TODO/checklist tool, whose handler is registered only when `update_plan_enabled` is true. The accepted profile explicitly requires `tools.update_plan.enabled: false`. A text-plan item does not authorize this native tool. [Plan handler](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/tools/handlers/plan.rs), [conditional registration](https://github.com/openai/codex/blob/78c290807ce710180111df227df3b7a4fe845452/codex-rs/core/src/tools/spec_plan.rs), accessed 2026-09-10. Model rerouting, hooks, environments, raw upstream-response delivery, collaboration, MCP, files, commands, native image operations, account login, every other known-but-unadmitted method and all future methods remain terminal. This conservative route may still stop on legitimate client activity outside the audited reviewer profile; no whole-client compatibility guarantee is made.

An effect notification is retrospective evidence, not proof that an effect was prevented. These guards do not replace the original enforced process boundary, tool/configuration restrictions or broker authority checks, and do not attest that the native registered tool inventory is empty.

Before validating an item notification, the session retains a fixed categorical observation: known method or `unknown`; phase; known item type or `unknown`; identifier-valid and thread/turn bound/matching booleans; turn-start/completion state; acceptance/refusal. No item ID, text, arguments, unknown field/method/type string, raw payload or payload digest is included. Snapshot item failures receive their own categorical snapshot observation. Item-policy failure codes and outer-notification refusal codes are separately preserved from broker failures. The first session failure remains `primary_failure`; a later cleanup failure is appended to `additional_failures` instead of replacing the first cause. Parent host-input/cache comparisons remain separate integration work.

## Offline validation

`python3 -m unittest discover -s tests -p test_p3_lifecycle_030.py -v` passes 26 tests, including the two parent-added cache-descriptor integration cases. These exercise:

- Exact equality of the 19 item discriminants and 81 notification labels with archived source; all 12 prohibited item classes remain terminal. Minimal prohibited fixtures exercise the class guard and are not represented as full valid effect schemas.
- Full source-shaped compaction and text-plan lifecycles; retained binding, registry, callback history and monotonic counters; malformed/foreign identities, replay, type changes, unknown/private strings, unsupported notification families and item-count exhaustion.
- The original broker behind a generated Python pipe responder: a correctable argument error, two compactions, a plan/delta, a successful evidence read and an exclusive synthetic dependency-verdict transport. The file is explicitly engineering data and is deleted with its temporary fixture; it is not an independent scientific verdict.
- Eight argument errors across eight compactions still stop the ninth request at the original broker/interface ceiling. The actual synthetic read and path-refusal witness also survive compaction.
- A prohibited item before verdict leaves output absent. A deliberately reported cleanup failure preserves the earlier lifecycle failure; the generated responder is actually reaped by the test.
- Ordinary buffering metadata interleaved with compaction and broker operations leaves the selected model and controls unchanged. Malformed, foreign or model-mismatched metadata stops; source-shaped metadata with more than 64 entries and strings longer than 256 bytes remains admitted within the existing frame limit; private metadata strings and their hashes are absent from reports.

No native client, model, authentication file or network operation is used by these tests. They establish deterministic controller behavior for these fixtures, not successful operation of the proposed integrated native route, adequacy of a scientific review after compaction, or the missing cause of 028. Any activation must follow the combined tested control-and-budget amendment prepared by the PI.

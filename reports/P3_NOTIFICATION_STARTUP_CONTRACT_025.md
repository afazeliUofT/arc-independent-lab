# Session024 notification and startup design audit

Engineering judgment only. No native client, authentication, model operation, code edit, or scientific review was performed by this audit. The exact installed version remains Codex 0.151.0, upstream commit `78c290807ce710180111df227df3b7a4fe845452`. Work is based on the archived installed schemas and source, plus additional exact source retrieved by the sibling source audit. This is a design assessment, not permission to launch.

## Established observation

The attached `REPORT(20260909-213441).json` has SHA-256 `60f7a041d8415990a28362459e4ddd1b6029f10c1066d92ab85e0c6efee25c5f`. Its synthetic stage sent and accepted thread/start and turn/start, admitted one existing bubblewrap config advisory, remote-control disabled, thread/started and all eight source-derived deprecations, then stopped on method `warning` with the startup window still open. It dispatched zero broker requests, observed no synthetic read/refusal, and produced no verdict. The warning payload was discarded. Its text, origin, effect and benignity are not established by its position after eight notices.

The authoritative accounting is five observed native starts and two sent explicit turns against six/three approved cumulative maxima: one start and one turn remain. Sent turns count without output; backend inference, token use and charges remain unknown.

## Startup ordering and the missing barrier

Exact `core/src/session/session.rs:1006–1037` queues legacy deprecations, configuration startup warnings, then the optional unstable-feature warning. Hook startup warnings are appended later at 1296. At 1472–1506, the core emits SessionConfigured and that vector in order. This is core queue order, not a client-facing ready signal.

Exact `app-server/src/request_processors/thread_processor.rs:1516–1595` attaches a listener and then sends thread/start response and thread/started from the request task. `thread_lifecycle.rs:289–400` spawns the event listener asynchronously; it selects listener commands before core events. `thread/started` therefore does not attest that startup warning delivery finished. Core `SessionConfigured` is first, so it cannot be a tail marker either. `thread/read` uses live/persisted snapshots (`thread_processor.rs:2771–2863`), not a warning-queue drain. An empty turn/start response binds a turn and says nothing about prior notification delivery.

There is a further independent producer: `app-server/src/extensions.rs:247–304` queues ExtensionWarning as a listener command or spawns a task waiting up to ten seconds for a subscriber. It discards the extension turn identifier and truncates the message at 256 UTF-8 bytes. Thus a thread-bound generic warning is not necessarily a core startup-vector member. Neither a quiet interval, thread/started, account/model RPC response, nor eight deprecations is an established complete startup barrier in the pinned public protocol.

Current024 calls request(turn/start) inside its thread/start response handler after draining only the `early` list of already parsed frames. Frames after the response in the same OS read, unread pipe frames, and future listener output have not been admitted at that point. This can waste a sent turn. A concrete improvement is to defer enqueueing turn/start until the current receive batch has been parsed, and process already readable startup frames before writable turn bytes. Record this as opportunistic preturn draining, never a completion proof. Waiting for a finite set of mandatory source-predicted notices can avoid the known race only when the set is actually derivable from admitted full configuration; it still cannot establish absence of other producers.

The override profile contains false controls, not the entire effective [features] table. The optional unstable-feature warning depends on inherited explicit true features as well as source stages. Its exact list or even mandatory presence cannot be inferred from the override subset. Do not turn a guessed last warning into a readiness sentinel.

## Notification contract: information versus consequential events

The embedded experimental schema has 79 ServerNotification variants. A protocol-defined method is not automatically an allowed effect. Conversely, a notification does not execute anything in the parent merely because it contains a model/capability-like word. The authority boundary remains the pinned profile/source/mount admission plus unchanged broker; notification guards are retrospective observations.

| Family | Narrow treatment and why |
| --- | --- |
| remoteControl/status/changed | Admit only source/schema-valid disabled state. Enabled/connecting/connected state contradicts the approved isolated route and stops. Installation/server identity fields are metadata, never capability grants. |
| account/rateLimits/updated | Validate schema and retain only fixed quota categories. It does not replenish budget or establish hosted ChatGPT allowance. Current code only checks a dictionary. A clearly exhausted/changed required meter should stop under the same headroom rule; sparse updates cannot replace explicit RPC admission. |
| account/updated | Current code ignores planType and permits null authMode before thread binding, including after explicit account admission. Exact account_processor.rs:200–209, 998–1014 shows null can represent no cached auth/logout. After baseline admission, any contradictory auth or plan observation must stop before turn; a same-value metadata refresh does not grant a new account route. No identifier values need enter reports. |
| thread/started | Source/schema-valid repeated metadata must match the trusted fresh ephemeral thread; duplicate or foreign identity stops. It is not startup-ready, capability-inventory, or scientific-independence evidence. |
| thread/settings/updated | Existing validate_thread_settings correctly compares model/provider/effort/permission/sandbox/instructions. Same-value settings are informational. Changed controls stop. multiAgentMode is compatibility metadata, not proof that delegation is impossible. Presentation fields and service-tier metadata cannot grant tools or spending. |

A future narrow handler can validate binding and unchanged selected model, ignore display/recommendation data, and never act on fasterModel. Parent never requests retry; notification absence cannot prove no native internal retry. All server requests except the exact bound broker call remain refused without action. |

## Concrete diagnostics and offline verification design

Add one bounded notification-receipt path before refusal, covering all known 79 schema methods with fixed output labels and unknown fallback. Record classification, decision, validated shape booleans, binding category, phase (prethread/thread_pending/thread_bound/turn_pending/turn_bound/activity), startup-window state, and queued/sent turn booleans. Counters and enum labels are sufficient. Do not store native method names outside the fixed method set, unknown field names, warning text, fragments, paths, arguments, text lengths, hashes, config values, credentials or raw stderr. Existing scopes prohibit retaining raw warning contents; preserve that protection.

Separate classification from admission. The source catalog should recognize consequential warning families to diagnose and stop, not to grant them. Full-string comparisons or exact grammar with source-enumerated values are preferable to permissive substrings. Prefix matches may be diagnostic-only. In particular, ExtensionWarning truncation means a prefix may conceal the distinguishing tail.

Use offline synthetic protocol fixtures for the full expected startup sequence and all relevant informational metadata, with messages before/after thread response, same-read trailing frames, turn-response buffering, split frames and immediate writable stdin. Verify no turn is sent when an already available disallowed warning is parsed. Also test malformed envelopes, duplicate/unbound IDs, required-field failures, false-versus-zero controls, late/duplicate notices, true authority effects and source warning fallbacks. These are engineering tests; none substitutes for actual synthetic broker refusal and separately fresh scientific review.

## Safer next step and budget

First examine whether the existing stopped run contains recoverable source-specific diagnostics without a native/model operation. The original report alone cannot supply them. An offline fixed-file probe is useful only with a clear source-supported location/format and privacy-preserving classifier; see the recovery notes below.

If that route cannot identify the warning, prepare a hard no-turn startup diagnostic: same pinned binary and existing-subscription/mount/profile/account safeguards, fresh runtime, only the existing initialization/read/thread-start request prefix, no turn/start constructor or broker-dispatch path, no retry, finite deadline/stream/tree limits, safe warning receipt and verified cleanup. Stop on consequential/unknown/malformed warnings or effects. A finite observation horizon ending without a warning reports `no_warning_observed_before_deadline`, never startup success or eligibility for science. Do not assert that it will reproduce a turn-time warning.

Such a diagnostic consumes at most the one remaining start and zero sent turns: cumulative six/two. It is materially narrower than another speculative model turn. However, unused capacity is not itself a reusable authorization token: exact024 scope says partial attempts are preserved and stop, ties authorization to a scope digest, and binds the actual controller. Do not rerun stale024, overwrite its receipt, reset counters or silently bypass its approval consumer. Parent must determine whether the user's present explicit instruction authorizes this concretely specified narrowing; if not, request only that diagnostic authorization after packaging it, not an unnecessary full-review cap increase before the warning is understood.

If no additional diagnostic start is used, completing required fresh synthetic plus fresh science needs cumulative seven starts/four turns (a genuine +1/+1 amendment to six/three). If the separate startup diagnostic uses the sixth start, the later two-stage operation needs eight/four (+2 starts/+1 turn relative to six/three). Do not omit either stage, resume the failed synthetic thread, count shared-workspace agent review as independent, or promise a verdict in return for the amendment. Defer the concrete full-operation amendment until the unknown warning and handler design are resolved.

## Offline log recovery assessment

The parent launches with `RUST_LOG=off` (`gate0_client_preflight.py:154–161`) and consumes/discards stderr. This suppresses its stderr subscriber, but **does not establish absent project logs**: pinned app-server/lib.rs:671–680 installs a separate `codex_state::log_db` layer whose default filter uses TRACE for ordinary targets. The source-defined current database is `runtime_state/logs_2.sqlite`; the source agent has archived the exact schema/filter. The queue is bounded at 2048 events, batch 512, flush interval ten seconds, so process teardown may lose undrained events.

The normal outgoing trace `app-server event: {notification}` logs the strum Display method label (`outgoing_message.rs:602`, protocol/common.rs:1597–1614), not WarningNotification.message. The thread listener contains no full-event debug log. `core/session/mod.rs:2272–2293` forwards events without full-message tracing; Warning is excluded by rollout persistence policy, and rollout trace needs an environment variable not forwarded by the parent. Therefore no general archive of the lost warning payload is established. Particular config producers separately tracing::warn their message could leave evidence; the unstable-feature advisory does not.

A useful offline probe must therefore be modest: exact original run directory, fixed source-derived DB and WAL names, no recursive host search, symlink/regular-file/size checks, strictly read-only access, fixed table/column validation and source-family classification only. Native logs may contain unrelated sensitive fields, so do not print/copy/hash raw records or read auth/config databases. Handle a surviving WAL explicitly; a main-file-only immutable SQLite open can miss WAL-resident records and cannot justify absence. Missing/corrupt/unflushed/unrecognized records yield unresolved. A producer log, even when matched, is corroboration of that producer event, not proof of the exact warning whose receipt was discarded unless ordering/binding evidence genuinely links it.

Remaining unknowns: exact rejected payload and producer; whether source-specific diagnostic records survived; relevant inherited enabled feature list; whether another warning appears only during turn setup/model use; actual model/backend access and quota charge; actual future synthetic refusal and substantive independent verdict. No offline schema exercise or source reasoning resolves those live observations.


## PI decision after combining the source audits

The thread-only diagnostic option discussed above is not selected. Exact first-turn source analysis shows that it cannot exercise model-metadata and Code Mode warnings compatible with the actual024 trace. The next action is a bounded offline inspection of preserved runtime logs and filtered, previously admitted configuration/cache metadata. It consumes no native start or model turn. If inconclusive, preserve that uncertainty and prepare a diagnostic-capable operation before any required native-scope amendment. Current full review is not reauthorized by this document.
